## 1. Problem and goal

Until now, a job on the owner's Debian server pulled every push to GitHub, built the hub and put it on the VPS: no test ran, the deploy bypassed the product's own install and upgrade path, and the build ran on a machine that is part of production. That job is off (owner, 2026-10-14), and nothing has been pushed since `main` (90 commits wait on `m0-foundations`).

**Goal:** every change is tested by machines before it reaches `main`; every candidate release is built once, signed, installed on a staging hub and its lab of real probes the way a user would install it, and tested there; production gets **the same binaries** after the owner approves them. The work is also a workshop: each phase is built so that how and why it works is clear, and each step says which general CI/CD idea it is an example of.

Three terms, used exactly:

- **Continuous integration:** every change lands on `main` soon, after machines proved it breaks nothing.
- **Continuous delivery:** every candidate *could* ship; shipping is a decision. **Production is continuous delivery** (the owner approves).
- **Continuous deployment:** it ships by itself. **Staging is continuous deployment.**

## 3. What exists and is kept

The release design already does most of what CD needs. Inspected 2026-10-14:

| Piece | Where | What it already gives CD |
|---|---|---|
| **Probe release:** binaries, `manifest.json` (version, each binary's SHA-256), `manifest.json.sig` (Ed25519 over the manifest's bytes) | `common::release`, `blentinelmake release build/sign` (D-55) | integrity of every probe binary; the probe checks it again before installing (it trusts neither hub nor network) |
| **Hub release:** `hub-<target>`, `probes.tar.gz`, `release.json`, `hub.sh`, `SHA256SUMS`, `SHA256SUMS.sig` | `common::hub_release`, `blentinelmake release hub` (D-57) | one signature covers every file; `hub.sh` checks it with `openssl`, `hub upgrade` with the keys compiled in |
| **`hub upgrade`:** only newer; self-test of the new program on a copy of the database; `-pre-upgrade` backup; switch; health for 90 s and stable 15 s; else program **and** database put back | `ops::hub_upgrade` (D-75) | the deploy step, its health check and its automatic rollback, already written and unit-tested (never yet run on a real systemd host: an open item this proposal closes) |
| **Probe rollout:** approval, canaries, soak, pause, signed rollbacks | D-74 | how a candidate reaches the lab's probes: the product deploys to its own test fleet |
| **Backups:** `hub backup`/`restore`, daily schedule, pre-upgrade | D-52, D-60 | what the restore drill restores |
| **The gate as cargo aliases:** `cargo lint`, `lint-wasm`, `test-all` | `.cargo/config.toml` | the one definition of the gate that CI and the developer both run |

### 3.1 Gaps found, and how this design closes them

1. **The trusted keys are compiled in** (`BLENTINEL_RELEASE_KEYS`, read by `release::trusted_keys` at build time). The same bytes must run in staging and production, so a binary can't trust "the staging key" in one place and not the other by being built differently. **Closed by key roles (§6.2):** a build compiles in two lists, production keys and staging keys; staging keys count only on a machine that opted in locally.
2. **The version is compiled in** (`CARGO_PKG_VERSION`; `hub self-test` requires it to equal `release.json`). A build called `0.1.0-rc.3` can't become `0.1.0` without rebuilding. **Closed by plain versions (§6.1):** every candidate is a full version (`0.1.4`); "candidate" and "release" are states, not version suffixes.
3. **The probe release's signature is inside `probes.tar.gz`,** which `SHA256SUMS` covers. A production signature changes that archive. **Closed by defining "the same binaries" precisely (§6.3):** promotion re-signs the unchanged `manifest.json` and `SHA256SUMS` lists; every `hub-*` and `probe-*` keeps its bytes, and promotion refuses if one hash differs from what staging ran.
4. **An armv6 probe would take the armv7 binary:** `Platform::current` matches on `std::env::consts::ARCH`, which is `arm` for both. On the Pi Zero W, self-update would install a program that can't run there (the watchdog would roll it back, and the probe would never update). **Closed in phase 2** by an `arm-unknown-linux-musleabihf` platform told apart at compile time, if its C crypto library builds and passes its tests for armv6; otherwise armv6 is declared unsupported. (Inspected in phase 2: the probe's TLS is `rustls` on **`aws-lc-rs`**, not `ring`; with SQLite, the C code an ARMv6 build must get right. D-104.)
5. **A probe release is approved only in the web UI,** and the hub has no API tokens yet (M1-07). The agent can't approve a candidate on the staging hub. **Closed in phase 4** by `hub release approve <version>` on the server, run as root like `hub upgrade` (D-75: the server does, the page tells).
6. **No release records the commit it was built from.** **Closed in phase 2:** `release.json` gains `commit` (it is covered by `SHA256SUMS`, so it is signed); GitHub's build provenance attestation is added beside it (§6.4).

## 5. The pipeline

```
developer: branch → blentinelmake ci → push → pull request
   │
   ├─ GATE   (every push to a PR; required to merge; GitHub-hosted)
   │    fmt · lint · lint-wasm · test-all (Linux, Windows) · deny · browser tests
   │
   ├─ merge to main (merge commit)
   │
   ├─ FULL   (every merge, and nightly)
   │    builds for every target, once: static-link check, SHA256SUMS
   │    install tests and the upgrade-rollback test on systemd
   │    macOS and FreeBSD: build + unit tests, informational
   │
   ├─ tag v0.1.N (= [workspace.package] version, on main)
   │    build (no secrets) → sign with the STAGING key (environment "staging",
   │    tags only, no build step) → GitHub pre-release v0.1.N + provenance
   │
   ├─ STAGING (continuous deployment, pull)
   │    lab-control (timer, outbound only): new pre-release?
   │      → download → verify (signature, every sum) → record hashes
   │      → staging: hub upgrade --from <verified folder>
   │      → hub release approve 0.1.N → lab probes update (canary first)
   │      → smoke tests, every lab probe reporting on 0.1.N, its checks green
   │      → GitHub Deployment status: success/failure, with the record
   │    then: soak (a day or more), the owner's exploratory testing
   │
   └─ PRODUCTION (continuous delivery, the owner approves)
        the owner, offline: verify staging's record → sign the SAME lists with
        the PRODUCTION key → upload the signatures → mark v0.1.N the latest release
        → the VPS: hub upgrade · the owner's probes: rollout, canary first
```

Each arrow is a gate: a failure stops the version where it is. A version that fails in staging is never promoted, and the next one is a new number (roll forward).

**Revised (owner, 2026-10-22, D-106):**
- Until the owner approves release readiness (ROADMAP M10-07), the `tag` and `PRODUCTION` steps aren't used: no tag, no pre-release, no public release.
- Staging is fed by **internal development builds** instead (§10.4). Every merge to `main` that passes FULL is versioned `-dev.N`, signed with the staging key in a job that builds nothing, and kept as a workflow artifact.
- The STAGING steps are unchanged. Proving them now is the point of phase 4.

## 6. Release integrity

### 6.1 Versions

- One version for the workspace (`[workspace.package] version`), SemVer, starting at **0.1.0**.
- **Every candidate is a full version.** Tagging `v0.1.N` on `main` makes candidate 0.1.N; CI refuses a tag that differs from the workspace version, or that isn't on `main`. A version is never re-used: a fix is 0.1.N+1.
- **State, not suffix:** a candidate is a GitHub *pre-release* signed by the staging key; a release is the same version, signed by the production key, marked *latest*. Versions that were never promoted are gaps in production, which is fine (a probe only needs newer).
- **Internal development builds (D-106)** are versioned `<workspace version>-dev.<N>`, where N is the Build workflow's run number. They are never tagged, never published as a release and never promoted. A `-dev` version orders before its release (`0.1.0-dev.N` < `0.1.0`), and dev builds order by N **as a number**. Today `Version` compares the part after `-` as text, so `dev.10` would come before `dev.9` (and `rc10` before `rc9`). Phase 4 fixes it to SemVer's rule, numeric identifiers as numbers.
- GitHub's `releases/latest` excludes pre-releases, so `hub.sh` and `hub upgrade` (whose default is `releases/latest/download`, D-57, D-75) never see a candidate. A machine only gets one by asking for its tag.

### 6.2 Keys and their roles

| Key | Private half | Signs | Trusted by |
|---|---|---|---|
| **Production** | offline, the owner's build machine only (D-55, unchanged) | promoted releases | every Blentinel binary |
| **Staging** | a secret of the GitHub environment `staging` | candidates | only machines that opted in to staging |

- A build compiles in both public lists: `BLENTINEL_RELEASE_KEYS` (production, as today) and `BLENTINEL_STAGING_KEYS` (new). Public keys aren't secrets; CI takes them from repository variables.
- **Staging keys count only where the machine said so:** on a hub, `[upgrades] staging = true` in its config file (a place on the server, like `release_url`: root decides it, the web UI can't); on a probe, a setting `probe install --staging` writes on the machine, which the hub can't change (zero trust: a hub must not be able to widen what its probes accept). `hub.sh` takes `BLENTINEL_STAGING=1` for a fresh staging install.
- **Why:** a leaked staging key can sign something only staging machines accept. Production hubs and probes ignore it, so the offline production key still alone decides what production runs. This is why the staging key may live in CI and the production key may not.
- The two signing steps reuse what exists: `manifest.json.sig` and `SHA256SUMS.sig`, the same Ed25519 over the same bytes; only the key differs.

### 6.3 "The same binaries"

- The binaries are built **once**, by the tag's workflow, and never again for that version.
- Promotion produces new signature files and therefore a new `probes.tar.gz` (the probe manifest's signature lives inside it) and a new `SHA256SUMS`. What doesn't change, and is checked: every `hub-*` and `probe-*` file, `release.json` and `manifest.json`, byte for byte. The promotion command (`blentinelmake release promote <version>`, phase 6) downloads the candidate, verifies its staging signatures and the staging deployment record, re-signs, and refuses if any binary's hash differs from the record.

### 6.4 What is recorded

- **In the release (signed):** `release.json` gains `commit` (the full SHA the tag pointed at); `manifest.json` lists every probe binary's SHA-256; `SHA256SUMS` lists every file.
- **Provenance:** the tag workflow adds GitHub's build provenance attestation (`actions/attest-build-provenance`) for each binary: a signed statement that this file was built by this workflow from this commit, checkable with `gh attestation verify`. It complements the release signature (which says *who* approved), it doesn't replace it.
- **Per deployment:** `lab-control` keeps a log line per deployment (time, version, commit, SHA-256 of `SHA256SUMS`, each binary's SHA-256, result) and sends the same as the GitHub Deployment's payload and status. Promotion reads it back.

## 7. Repository protection (phase 1)

Done in GitHub's settings by the owner, following the step-by-step list phase 1 writes in `docs/ci.md`; the workflows enforce their half in code.

| Protection | Setting | Why |
|---|---|---|
| `main` | a ruleset: changes by pull request only, the gate's checks required, no force push, no deletion | nothing reaches `main` that the gate didn't pass; history can't be rewritten |
| Tags `v*` | a ruleset: only the owner creates them, none deleted or moved | a tag is a release: moving one would change what a version means |
| Workflow token | default permissions **read**; each job asks for what it needs (`contents: write` only to publish a release) | a compromised step can't push code or change settings |
| Fork pull requests | "Require approval for all external contributors" | a stranger's workflow change doesn't run until the owner has read it |
| Actions allowed | GitHub's own and a short list, **every third-party action pinned to a full commit SHA** (with a comment naming its version); Dependabot proposes updates | a tag like `@v4` can be moved to malicious code; a SHA can't |
| Secrets | only the staging signing key, only in the environment `staging`, which accepts tags `v*` only; the signing job builds nothing | a pull request never sees it; a malicious dependency's build script runs in the build job, which has no key |
| Runners | no self-hosted runner registered at all; workflows say `ubuntu-latest`, `windows-latest`, etc. | the strongest guarantee: there is nothing on the LAN a workflow could target |
| `pull_request_target` | never used | it runs with the base repository's secrets on a fork's code |
| Caches | written only by runs on `main`; pull requests read them | a pull request can't poison what `main` builds with |
| Checkout | `persist-credentials: false` | the token isn't left on disk for later steps |

## 9. Phase 2: build once (first half of M0-13)

- On every merge to `main` and nightly: build every target once (probe: x86_64, aarch64, armv7, armv6 if supported, Windows; hub: x86_64 Linux), check the Linux binaries are static (no OpenSSL or other library: FP-2), write `SHA256SUMS`, keep them as workflow artifacts.
- Install tests on the runner's real systemd: `hub.sh` from a folder, `probe install`, enroll, report, uninstall.
- **The rollback test:** install a hub, then `hub upgrade` to a deliberately broken one, and check that the program and the database came back (D-75's rollback on a real service, never run until now). Built with a throwaway key that exists only for that job: a test build, not a release.

- `release.json` gains `commit`; the armv6 platform (gap 4) is settled here.

## 10. Phases 3 and 4: `lab-control` and staging

### 10.1 Two kinds of change, two paths

| | Configuration | Deployment |
|---|---|---|
| What | the machines: users, packages, firewall, the agent itself, SSH keys | a new Blentinel version on staging |
| Tool | Ansible, playbooks in `ops/` | the agent: a systemd timer and one script |
| Who starts it | **the owner**, after reading the change | the timer, every 5 minutes |
| From what | a checkout of `ops/` the owner updated on purpose (`git fetch`, `git diff`, `git merge --ff-only`, then `ansible-playbook`) | a release that passed verification |
| Never | applied by a timer or from an unreviewed download | runs a playbook, a script or any code from the release other than the verified Blentinel binaries |

This is decision 2 of §2 made concrete: a pushed change to `ops/` does nothing until a person applies it.

### 10.2 The agent

Installed by Ansible as a fixed script, owned by root, run by an unprivileged user `deployer`:

1. Ask GitHub's API for the newest pre-release (outbound HTTPS; a fine-grained token for this repository with *Deployments: read and write* only, used to post statuses). **Revised (D-106):** the newest internal development build instead (§10.4); the token then also needs *Actions: read*, to download it.
2. If it is newer than staging's version: download its files into a new, empty folder.
3. Verify with the staging public key, which is pinned in the agent's configuration (never taken from the download): `SHA256SUMS.sig` with `openssl` (as `hub.sh` does), then every file against `SHA256SUMS`. Any failure: stop, report, change nothing.
4. Write the deployment record (§6.4), create the GitHub Deployment (`environment: staging`).
5. Copy the verified folder to staging and run the deployment there over SSH, with a key that `authorized_keys` restricts to **one forced command**: a wrapper that takes a version, finds the folder for it, and runs `hub upgrade --from <folder>` then `hub release approve <version>`. That key can do nothing else, whatever the agent sends. `hub upgrade` checks the signature again with its own keys (defence in depth).
6. Smoke tests: the staging hub answers and is on the version; within a time limit every lab probe reports on the new version; their checks are in their expected state.
7. Post the result as the Deployment's status.

### 10.3 Ansible

- `ops/` holds generic playbooks and roles: `lab-control` (the agent, its user and timer), `staging` (base of the hub's machine), `lab` (base of the probe machines: Pis over SSH, the Windows VM over SSH or WinRM, FreeBSD), `production` (base of the VPS: users, firewall, updates).
- **Ansible calls Blentinel's installers, never re-implements them:** it runs `hub.sh` and `probe install`, it doesn't copy binaries or write unit files. Otherwise the deployment would test the playbook instead of the product.
- The inventory and its secrets (Ansible Vault) are on `lab-control` only.
- Optional: Terraform (OpenTofu) creates the lab's VMs on XCP-ng through Xen Orchestra, so a broken VM is destroyed and recreated by one command.

5. **The drill's container:** **rootless** `podman --network none`, from Debian's packages, kept in phase 4 (owner). The alternatives were `systemd-nspawn`, or moving the drill to phase 5.
6. **GitHub settings, by the owner:** the environment `staging` restricted to the branch `main`, with the staging key as its only secret; the repository variable `BLENTINEL_STAGING_KEYS`. (Part C: the signing job uses the environment with `deployment: false`, so signing records no deployment and staging's deployment history stays the agent's: D-107.)
7. **Artifacts are unlisted, not secret:** on a public repository, anyone signed in to GitHub can download a workflow artifact. Staging-signed builds are trusted by staging machines only, so this is acceptable unless the owner says otherwise.

**Phase 4's "done when" (revised):** a merge to `main` reaches the staging hub and its probes as an internal development build with no one touching it, and GitHub shows the result, with no tag and no public release.

## 11. Phase 5: the lab in the loop

- The Pi 4, Pi 3, Pi Zero W, Windows VM and FreeBSD VM run probes enrolled to the staging hub, permanently. Each candidate reaches them through the staging hub's rollout (canary first), so every candidate tests self-update and the real checks on every platform.
- A lab machine that is offline marks the deployment *degraded*, not failed (a Pi being rebooted shouldn't block a release); a probe that is online and didn't update, or whose checks are in the wrong state, fails it.
- A flaky result is fixed or quarantined with a `known_issue_*`-style note, never retried until green.

## 12. Platforms and support levels

| Level | Means | Platforms |
|---|---|---|
| **Supported** | built and tested on every change; in releases; lab-tested on real hardware | Linux x86_64, aarch64, armv7, armv6 (probe; hub x86_64), Windows x86_64 (probe) |
| **Candidate** | built and unit-tested in CI, informational | macOS; FreeBSD (armv6 was one until phase 2 settled it: supported, D-104) |
| **Unsupported** | not built | everything else |

FreeBSD and macOS become supported only through a port (a roadmap item each): a service manager (rc.d, launchd) and the checks' code for those systems. CI makes the gap visible; it doesn't close it.

## 13. Rollback and recovery

- **Roll forward first.** A bad version is fixed by the next one; the pipeline makes that hours, not days.
- **Automatic rollback stays** (D-75): a hub that doesn't come up healthy is replaced by the old program and the pre-upgrade database. Phase 2 tests it on a real service; phase 4 can force it on staging with a deliberately broken candidate.
- **Migrations that can't go back:** every deployment record says whether the version migrated the database (its migration count changed). Such a version can be undone only by `hub restore` of its `-pre-upgrade` backup, which loses what happened since; promotion shows this beside the approval.
- **The backup/restore drill** (phase 4, weekly by the agent): take staging's newest backup, restore it on `lab-control` in a throwaway container **without a network** (a backup holds the hub's private key: a restored copy on the network would be an impostor of the staging hub to the lab's probes), run `hub doctor` and compare counts with the source, then destroy it. A backup that was never restored isn't known to work.
- **N−1 database compatibility** (an older hub opening a newer database) is not done during pre-alpha (D-30). Before 1.0, or before hosting hubs for others (M8-06), it gets its own decision.

## 14. Tools considered

| Tool | Verdict |
|---|---|
| **GitHub Actions** | **Chosen** for CI and release packaging: hosted runners for every OS, free for a public repository, the pipeline in the repository. |
| **Jenkins** | Not used. It does the same job (a `Jenkinsfile` is a pipeline as code, its agents are runners) but is a server to run, patch and secure, and the builds would run on the LAN. Worth one exercise later: the same pipeline in a Jenkinsfile shows the ideas are the tool's, not GitHub's. |
| **Ansible** | **Used** for configuration (§10.3), applied by a person. |
| **Terraform / OpenTofu** | Optional, for the lab's VMs on XCP-ng and the VPS. |
| **Woodpecker** | Removed (`.woodpecker.yml`). |
| A second, private repository with a self-hosted runner | Rejected by the owner: two repositories to keep in step. |
| A self-hosted runner on the public repository | Rejected: GitHub advises against it; a fork's workflow could target it. |
| A hosted runner joining the LAN over a VPN | Rejected: a third-party service and a key in GitHub that opens the LAN. |
| An inbound webhook | Rejected: an open port into the LAN. |
