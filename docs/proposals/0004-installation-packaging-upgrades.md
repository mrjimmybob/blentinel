## 1. Problem

Installing today requires:

- **A Rust toolchain, `wasm32` target, and `cargo-leptos`**, because the README's install instructions are really build instructions.
- Building per target and zipping a `publish/` folder by hand. `publish/` currently holds 9 timestamped zips.
- Copying a whole `app/` directory (binary + `site/`) for the hub.
- Hand-writing systemd units or PowerShell `sc.exe` scripts from the README.
- The 5-step key-exchange dance and a custom probe build for HTTPS.
- Manually upgrading every probe on every client machine.

## 2. Targets (acceptance criteria)

| Scenario | Target |
|---|---|
| Fresh hub on a Linux VPS | **≤ 5 min**, one command, ends at the setup wizard URL |
| Fresh hub on Windows | Download → `hub.exe install` → browser |
| Fresh hub via Docker | `docker compose up -d` with the documented compose file |
| New probe on Linux/Windows | **One command** from the "Add probe" wizard, reporting within 1 minute |
| Upgrade hub | Replace the binary / `hub upgrade`; automatic DB backup + migration |
| Upgrade 100 probes | One click in the UI (staged), with automatic rollback on failure |
| Uninstall probe | `probe uninstall` removes the service and directory; nothing left behind (FP-2) |

## 3. Principle check

| | |
|---|---|
| FP-1 | Probes **download** upgrades from the hub or the release server (outbound). The hub never pushes. ✔ |
| FP-2 | Static musl binaries; `install` sets up the service with OS-native mechanisms, no installer framework. ✔ |
| FP-3 | Release binaries are signed. Probes verify the signature before swapping. The hub download is pinned. ✔ |

## 4. Design: hub

### 4.1 One binary

- Web assets (WASM, JS, CSS, images) are **embedded** in the hub binary (`rust-embed`/`include_dir`), so there's no `site/` folder to deploy (D-11).
- Release targets: `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-pc-windows-msvc`. Docker image: `FROM scratch` / distroless + the musl binary, multi-arch.

### 4.2 CLI

```
hub install   [--data-dir DIR] [--port 443] [--http-port 80] [--no-service]
              creates data dir + bootstrap config, generates keys and self-signed TLS,
              registers the system service (systemd unit or Windows service), starts it,
              prints:  https://<host>:<port>/setup   setup code: XXXX-XXXX
hub uninstall [--keep-data]
hub status    service state, version, DB size, probes online, cert expiry
hub backup    [--out FILE]      online SQLite backup (VACUUM INTO) + keys + config → .tar.gz
hub restore   FILE
hub user ...  (0001)
hub doctor    checks ports, cert, permissions, disk space, clock
```

### 4.3 One-line install (Linux)

```sh
curl -fsSL https://get.blentinel.dev/hub.sh | sudo sh
```

The script detects the architecture, downloads the release plus `SHA256SUMS` and its signature, verifies them, puts the binary in `/usr/local/bin/blentinel-hub`, and runs `hub install`. The script is short and readable, and is also published in `docs/install/hub.md` for people who don't pipe to `sh`. (The domain is a placeholder; the release host is to be decided.)

### 4.4 TLS

HTTPS is on by default (D-03), with three documented options:

1. **Auto self-signed** (default; works immediately).
2. **ACME/Let's Encrypt** (`[tls] acme_domain = "hub.example.com"`) for internet-facing hubs.
3. **Behind a reverse proxy** (Caddy/nginx/Traefik examples); plain HTTP on localhost only.

### 4.5 Backups and upgrades

- Scheduled backups are configurable in the UI (daily, keep N), written to the data dir or a configured path.
- On start, if migrations are pending: **automatic backup → migrate → start**. A failed migration restores the backup and exits with a clear message.

## 5. Design: probe

### 5.1 Distribution

- Release targets: Linux musl `x86_64`, `aarch64`, `armv7` (Raspberry Pi); Windows `x86_64` (later `aarch64`); macOS optional (P3).
- The **hub serves probe binaries**: releases bundle all probe builds, or the hub fetches matching ones from the release server. Endpoint: `GET /download/probe/{os}/{arch}`. Clients download from the hub they already need to reach, so no extra firewall rule is needed.

### 5.2 One command (generated by the "Add probe" wizard, per OS)

**Linux**

```sh
curl -fsSL --pinnedpubkey 'sha256//<hub-spki-b64>' -k https://hub.example:3443/install/probe.sh \
  | sudo sh -s -- BLT1-7Q4M-….
```

`--pinnedpubkey` makes the download from a self-signed hub **safe** because curl verifies the pinned key (the `-k` only disables CA validation). The script downloads the right binary (also pinned) and runs `probe install --code …`.

**Windows (PowerShell, as admin)**

```powershell
$c='BLT1-7Q4M-…'; iwr https://hub.example:3443/install/probe.ps1 -UseBasicParsing | iex
```

For hubs with self-signed certs, the wizard instead offers "download `probe.exe`" (from the hub page the admin is already on) plus `probe.exe install --code BLT1-…`. The probe itself then pins everything.

**RMM / GPO mass deployment:** a multi-use enrollment code (0002) + `probe.exe install --code … --quiet`.

### 5.3 `probe` CLI

```
probe install --code CODE [--dir DIR] [--quiet]
    copies itself to the standard location
      Linux:   /opt/blentinel-probe/       (service user 'blentinel', cap_net_raw set on the binary)
      Windows: C:\Program Files\Blentinel\Probe\  (data in C:\ProgramData\Blentinel\Probe\)
    enrolls (0002), writes bootstrap config, registers + starts the service
      (systemd unit with Restart=always; Windows service with failure-restart actions)
probe uninstall [--keep-data]
probe status     enrolled? probe id, hub, last successful report, queue depth, config version
probe doctor     DNS → TCP → TLS pin → handshake key → clock skew → report round-trip, with fixes
probe run        foreground (for debugging)
probe run --standalone checks.toml   developer mode (0003)
```

- `install` is **idempotent**: re-running it with a new code re-enrolls in place.
- Non-root and non-admin installs are possible with `--dir` + `--no-service` (e.g. restricted environments). Documented limitations: ICMP may need privileges, so TCP-connect ping can be used as a fallback.

### 5.4 Self-update (M4, FP-1 compliant)

> **Superseded by [0012](0012-probe-self-update.md)** (D-40): the full design, with phase 1 moved to M2. Kept below for history.

1. Admin chooses a target version: globally, per company, or for a **canary** set of probes.
2. `ReportAck` includes a `upgrade { version, sha256, url }` command (0003).
3. The probe downloads over its pinned connection and verifies **the release Ed25519 signature**. The release-signing public key is compiled into the probe. That's a vendor key, not a per-hub key, so it doesn't conflict with D-01.
4. It swaps the binary (keeping `probe.prev`) and restarts itself through the service manager.
5. **Rollback:** if the new version doesn't report successfully within N minutes, a watchdog (the service recovery action plus a startup check) restores `probe.prev` and reports the failure.
6. The hub UI shows the version distribution and rollout progress. Probes older than N−1 are flagged.

## 6. Release engineering (M0)

- GitHub Actions release workflow on tag `v*`: build matrix → static-linkage check → tests → `SHA256SUMS` → Ed25519 signature → GitHub Release + container registry.
- CI calls `blentinelmake` (D-21). `publish/` leaves the repo (it's already untracked, and should be git-ignored).

## 7. Tests

- CI: install/uninstall smoke tests in a clean container (Linux) and on a Windows runner (service registration). `probe status` must report "active" after install against an in-CI hub.
- Unit: path layout per OS, systemd unit rendering, signature verification, rollback decision logic.
- E2E: upgrade from vN-1 → vN with a deliberately broken vN → rollback observed.
